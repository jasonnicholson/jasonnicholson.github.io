# Verification: pade-approximation
## A1 — confirmed
- What I checked:
  1. Code path: `series_coeffs_analytic` has no branch for `gamma(x)` or `bessely(0,x)`, so cases 22–27 fall through to `series_coeffs_fit` (line 176). That routine (lines 179–229) samples f in Float64 at 29 points c + h·t, t = -14..14 (h = 0.01, 0.02, 0.03, 0.1, 0.05, 0.02 for cases 22..27), least-squares fits a degree-8 polynomial (BigFloat solve), and divides by h^k.
  2. Dumped the coefficients the script actually uses (copy of lines 1–229, `verify/dumpcoef.jl` -> `verify/fitcoefs.txt`) and compared them with exact Taylor coefficients from `mpmath.taylor` at 50 digits (`verify/exact.py` -> `verify/exactcoefs.txt`).
  3. Whether precision matters: re-did the same fit at 60 digits in mpmath with (a) exact samples and (b) samples rounded to Float64 (`verify/precision.py`).
  4. Drawn vs true curves: for all 45 (m,n) frames of each case, compared the script's drawn curve (fitted coefficients, script's own Padé solver, same clamping) with the true Padé approximant from exact coefficients. I did this two ways: the script's solver with exact coefficients (`verify/compare.jl` -> `compare.txt`), and independently `mpmath.pade` at 50 digits (`verify/hp_pade.py` -> `hp_pade.txt`). The second used a strict metric: points off by more than 3 px (plot area about 430 px tall), not counting ±3% of the x-range around any real pole of either curve.
  5. Rendered overlays (`verify/overlay_*.png`) and checked them against committed frames.
- Evidence:
  - Relative error of the fitted coefficients (k = 0..8). k ≤ 4: at most 2.5e-4. k = 5,6: up to 3.5e-2 (case 23, a5). k = 7,8: 1.1e-2 to 1.26e-1. The worst is case 26, a7 = 6.658e-7 against the exact 5.910e-7 (12.6%). Others: case 22 a7/a8 4.5%/5.0%; case 23 a5/a7/a8 3.5%/5.8%/4.6%; case 24 a7/a8 1.9%/2.0%; case 25 a7/a8 5.5%/6.9%; case 27 a7/a8 3.4%/4.1%.
  - Precision: exact samples and Float64 samples give the same relative errors to two digits for every coefficient. The error is truncation and aliasing: the degree ≥ 9 terms over the ±14h window leak into a5..a8. Sample roundoff does not cause it, so the BigFloat solve does nothing to help.
  - Visible differences, using the strict pole-excluded metric: case 22: 22/45 frames; case 23: 15/45; case 24: 11/45; case 25: 9/45; case 26: 2/45; case 27: 11/45. That is 70 of 270 frames, nearly all with m+n ≥ 5. Examples:
    - Case 22 [2/5] (frame 31): the true Padé has a pole at x ≈ 0 matching Γ's pole and follows Γ to about x = 3.3. The drawn curve (identical to committed frame_031.png) has no pole there and turns down after about x = 2.7.
    - Case 23 [0/8] (frame 37): the drawn curve has a pole at x = 0.001, while the true approximant has none near 0 in the window. The drawn outer pole is at 4.10; the true one is at 4.20. Committed frame_037.png shows the drawn version.
    - Case 27 [6/1] (frame 35): the drawn curve peaks at about +0.34 near x = 7.4. The true curve peaks at about 0.03 and falls off earlier, a difference of up to 1.09 in y (about 117 px).
    - Case 22 [6/1], [5/3], [7/1]: differences of 230–312 px.
    - Case 24 [3/5]: 307 px at the right edge.
  - Cases 22–24 also have many frames where poles shift slightly (for example 3.506 vs 3.552), and Froissart-like spurious real poles appear only in the drawn version (case 22 [1/6]: drawn poles at 0.821 and 3.41, true at 0.017 and 3.179).
- Severity: Error is fair. These frames are labelled "Padé [m/n]" but plot rational functions built from wrong series coefficients, so they are not the [m/n] Padé approximants of Γ or Y0. The low-order frames (m+n ≤ 4) are accurate, and case 26 is only mildly affected (2 frames, at most 13 px).
- Correction to the allegation: the substance, the line numbers, and the "up to ~13%" figure (12.6%) are all correct. One nuance on "several percent": a7/a8 are off by 1.9–13% in every case, and a5 in case 23 is off by 3.5%. On precision: the higher-precision (BigFloat) solve does not matter. Exact samples reproduce the same errors, because the cause is truncation in the fitting stencil, not floating-point roundoff. "A substantial number of frames" is accurate for cases 22–25 and 27 but overstates case 26.
